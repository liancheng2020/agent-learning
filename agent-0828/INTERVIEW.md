# Agent 0828 面试材料（Day 20：整合与作品化）

## 30 秒介绍

> 我把前几天的能力——规则审查、RAG 规范引用、人工审批、Trace、Redis 缓存、故障降级和自动评测——整合成一个可一键部署、可当场演示的完整应用，而不是停留在对话 Demo。仓库里带 `docker compose` 一条命令起全栈、固定数据集的 Baseline/Tuned 评测对比、Demo 截图与 GIF，并用 20 条分层测试把“文档、资产、接口、故障”一起纳入回归。README 的结构（架构 / 技术选型 / 快速运行 / 评测结果 / 失败处理）本身也被测试守护，防止文档和实现漂移。

## 2 分钟演示

1. `cp .env.example .env && docker compose up --build -d`，`docker compose ps` 四个服务 healthy，打开 `http://127.0.0.1:8080`。
2. 前端提交一段 Diff，展示 finding、citation、`trace_id` 与 `cache_hit`。
3. 触发一个故障演练（如 `empty_retrieval`），展示降级标记与恢复建议。
4. 创建 Patch/部署审批，证明 `pending` 下生成接口 409，`approved` 后才产出 diff。
5. `python -m app.cli compare` 或 `POST /eval`，展示 Baseline→Tuned 的指标提升。
6. 打开 `docs/demo.png`、`docs/demo.gif`，说明这是可直接分享的演示资产。

## 关键取舍

- **为什么强调“可评测”**：Agent 的行为调整很容易靠感觉，所以用固定数据集量化命中率、引用正确率和通过率，让每次改动都有回归基线。
- **Baseline 与 Tuned 差在哪**：Tuned 强化了规则命中与检索/引用链路，因此命中率和引用正确率从 27%~45% 提升到 100%；延迟略升是因为 Tuned 做了更完整的工作，且本地是确定性规则模型，毫秒级差异不具线上代表性。
- **为什么把文档和演示资产纳入测试**：README 是作品的第一门面，最容易被改代码时遗忘；用测试断言必需章节、Mermaid 图和 demo 资产存在且非空，避免“代码更新、文档过期”。
- **为什么全部能力收敛到一个仓库**：面试时“能一条命令跑起来”比零散讲几个片段有说服力，组件边界用 compose 和健康检查固定下来。
- **失败处理与降级统一**：模型超时/工具异常/JSON 失败 fail-closed，检索为空降级不伪造引用，审批拒绝阻断高风险操作，Redis 故障自动回退内存缓存并标记降级。

## 高频追问

### 这些评测指标各代表什么？

Case 通过率=整体是否给出正确结论；问题命中率=该发现的问题有没有被规则/检索发现；引用正确率=给出的规范引用是否对应真实原文；JSON 合法率与工具成功率反映输出与依赖的稳定性。失败样本要区分“规则没发现 / 检索没召回 / 引用不正确”再分别调。

### 为什么 Tuned 延迟反而更高？

Baseline 命中少、算得少，所以更快；Tuned 增加了命中与引用核对的工作量。两者都是本地确定性规则模型的能力对比，不是真实模型延迟，不能外推线上。

### 从演示到生产还差什么？

真实 LLM/Embedding 的容量与成本验证、身份认证与 RBAC、审批审计导出、密钥托管、分布式 Trace/OpenTelemetry、任务队列与幂等键、并发压测、数据迁移备份、Prompt/知识库版本治理。要明确当前验证的是工程骨架与故障边界。

### 你如何保证演示不会“跑不起来”？

部署契约（compose 四服务、健康检查、env 必填项、Nginx 反代 `/api`）和演示资产都由测试守护，配合本地 SQLite/内存回退，任何没有外部依赖的环境都能先跑通核心路径。
