> 基于 D:/ys-basket-mini 前端源码整理，整理日期：2026-09-17。用于配合简历讲述，不是线上运行验收报告。个人职责、参与时间和实际成果请按真实经历补充；文中的改进建议不能讲成已经落地的成果。

## 1. 项目定位与讲述方式

### 一句话介绍

拾味篮子是一个基于 uni-app 和 Vue 3 的食品订购与库存提货微信小程序，覆盖商品选购、购物车结算、微信支付、提货发货和订单查询，并包含合伙人、提现及电子发票等业务入口。

它不只是商品展示页面：需要把商品、价格、优惠、地址、订单和支付状态连接起来，同时处理登录失效、接口数据精度和小程序跳转外部 App 的平台限制。

### 60 秒介绍

“这个项目主要解决食品购买和后续库存提货的问题。用户可以直接购买或者加入购物车，结算时根据商品类型和用户身份展示价格、优惠及地址信息；购买后的库存还可以申请发货。

技术上使用 uni-app、Vue 3、TypeScript 和 Pinia。比较值得展开的是三个点：第一，请求层统一管理鉴权，并防止旧会话的失败响应清掉新登录状态；第二，保留接口原始 JSON 文本，避免大整数订单 ID 在解析时丢失精度；第三，区分下单、调起支付、取消支付和再次支付，不把前端回调简单等同于订单最终状态。

项目还有小程序衔接外部 App 的场景，需要针对 iOS 和 Android 分别处理。”

以上是项目介绍，不等于个人贡献声明。面试时再加一句真实的“我主要负责……”，不要默认宣称整个系统由自己独立完成。

### 3 分钟展开顺序

1. 业务背景：为什么同时存在订购和库存提货，两条流程分别解决什么问题。
2. 个人职责：明确实际做过的模块，未参与的后端实现只讲接口边界。
3. 主流程：选商品 → 确认价格和优惠 → 创建订单 → 微信支付 → 查询订单状态。
4. 技术难点：优先选登录竞态或大整数精度，讲清楚问题机制与解决方式。
5. 设计取舍：前端提交锁不等于服务端幂等；页面金额不等于服务端可信价格。
6. 后续改进：密钥安全、支付结果对账、金额计算与关键链路测试。

## 3. 两条核心业务链路

### 3.1 商品订购与支付

~~~text
立即购买 / 购物车
  → 读取订单草稿
  → 加载商品信息、地址、合伙人信息
  → 计算价格与可用优惠，检查必要地址
  → 提交订单，拿到订单 ID
  → 获取微信支付参数
  → 调起微信支付
  → 分别处理成功、取消、失败，衔接订单页面
~~~

结算页面读取后删除订单草稿缓存，减少旧草稿重复使用；商品元数据按 ID 组织，不直接替换用户已选择的商品；提交处理使用 submitting 检查和 finally 释放状态。

需要区分三个概念：订单创建成功、客户端支付调用成功、服务端确认到账。它们不是同一个事件，最终支付状态应以服务端查询结果为准。

### 3.2 库存提货与发货

~~~text
选择库存商品和数量
  → 填写 / 选择收货地址
  → 选择运费优惠
  → 提交发货申请
  → 无需支付：进入结果或订单页面
  → 需要支付：调起运费订单支付
~~~

这条链路不是重新购买商品，而是围绕已持有库存申请履约，支付也可能仅针对运费。讲清这个区别比罗列页面数量更有价值。

## 4. 高频技术追问与回答

### Q1：为什么选 uni-app，而不是原生小程序？

可以回答：业务以表单、列表、结算和订单流转为主，Vue 技术栈有利于复用团队经验，uni-app 提供小程序 API 和页面组织能力。但跨端框架不能消除平台差异，支付、web-view、外部 App 唤起仍需要按平台处理和真机验证。

不要回答“一套代码天然兼容所有平台”，也不要编造开发效率提升比例。

### Q2：为什么同时需要路由守卫和请求鉴权？

路由守卫负责访问体验：哪些页面可以匿名浏览，哪些操作需要先登录，以及登录后回哪里。请求鉴权负责接口调用过程中的失效处理：页面打开后 token 仍可能过期。

项目对首页、个人中心及商品等部分页面允许公开访问；请求层统一携带登录信息，处理 HTTP 401 和业务层的登录失效响应。两层互补，但都不能替代后端鉴权。

### Q3：多个接口同时提示登录失效怎么办？

请求层用 isHandlingAuth 控制重复提示和重复跳转，并区分公开页、登录页和需要强制登录的情况。延迟跳转前还会再次检查状态，避免用户刚完成登录又被旧任务带回登录页。

重点不是“加一个布尔值”，而是统一入口、明确重置条件，并处理路由切换期间的状态变化。

### Q4：旧请求怎么可能把新登录踢掉？

典型时序：账号 A 发出请求 → 用户切换并登录账号 B → A 的请求迟到并返回 401。如果收到 401 就直接清空缓存，会误清 B 的登录态。

当前实现记录请求发出时的 token 和 userId，处理失效时与当前会话比较；会话已经变化，就不清除新会话。注意这不意味着旧请求成功返回的数据也都受到隔离，页面数据提交仍可以补充会话版本检查或请求取消机制。

### Q5：登录之后如何回到原页面？

记录目标页面，解析登录回跳参数，并对历史嵌套跳转做有限深度处理。返回 tabBar 页面使用 switchTab，普通页面使用 redirectTo，不能把两类路由混用。

当前对路径的检查不应宣传为完整安全白名单。后续可根据 pages.json 建立明确的内部路由允许列表。

### Q6：为什么订单 ID 不能直接使用 number？

JavaScript 的最大安全整数是 9007199254740991。超过这个范围的整数可能在 JSON.parse 时被舍入；解析后再 String(id)，只是把已经错误的数字转为字符串，原始位数无法恢复。

例如接口返回 9007199254740993，必须在原始文本仍存在时保留它，而不是等业务页面发现不对再处理。

### Q7：项目如何解决大整数精度？

请求使用文本响应，避免 uni.request 预先解析。parseApiResponse 先正常解析并遍历数据：ID 类字段规范成字符串；遇到不安全的 ID 或显式允许的大数字字段时，再用 json-bigint 从原始 JSON 按路径读取准确值。

这样既保留普通数值字段的使用方式，也避免把每个响应的所有数字都变成字符串。非白名单的不安全数值会报错，而不是静默放行。

边界：已经作为不安全 JavaScript number 传入的数据无法恢复，只能拒绝或让上游改为字符串。字段名识别也不是完整业务 schema，长期应推动后端统一返回字符串 ID。

### Q8：ID 精度处理是不是也解决了金额精度？

不是。ID 是标识符，转字符串即可；金额涉及小数计算、舍入规则和服务端计价。当前页面仍有 parseFloat 等浮点处理，不能宣称已经实现全链路财务精度保障。

改进方向：约定分等最小货币单位，或统一使用十进制定点方案，明确折扣计算和舍入顺序；服务端重新校验商品价格、优惠资格、库存和最终金额。

### Q9：优惠怎么算？能不能叠加？

页面区分个人价部分和批量价部分，当前折扣作用于个人价部分，而非整单所有商品。可以概括为：个人价小计 × 当前折扣率 + 批量价小计。

渠道优惠和优惠券通过 activeDiscountType 表达当前优惠类型，不是自由叠加；页面还存在渠道优惠可用时限制切换优惠券的交互规则。讲述时以源码规则为准，不概括成用户任意二选一。

另外，订购优惠和提货运费券属于不同业务，不应混在一个折扣公式里。

### Q10：提交按钮加 loading，能防止重复订单吗？

只能减少当前页面上的重复点击。结算提交函数有 submitting 入口检查，并在 finally 中恢复状态；但刷新、重试、网络超时或多设备提交仍可能重复请求。

真正的订单幂等需要服务端支持：例如幂等键、业务唯一约束及对同一次请求返回同一订单。当前仓库是前端，不能据此声称服务端已经实现。

还需要逐个检查其他提交入口，不能把结算页的保护扩大成“所有提交都已防重”。

### Q11：支付取消、支付失败、订单取消有什么不同？

用户关闭微信支付是取消本次支付，不等于业务订单被取消；支付失败可能需要重试；业务订单取消是另一项服务端状态变更。

公共支付方法会适配参数字段、检查必要签名参数，再调用微信支付并区分取消与失败。再次支付沿用已有订单 ID 获取支付参数，而不是重新创建订单。支付签名由服务端提供，不应放在前端生成商户签名。

客户端成功回调只用来驱动交互，最终到账应查服务端。网络中断时更合适的状态是“支付结果确认中”，而不是直接判定失败并重新下单。

### Q12：为什么用 Promise.allSettled？

商品、地址、合伙人信息可以并行获取，allSettled 允许分别处理结果，避免一个失败就丢掉所有已成功的数据。

但“页面可以展示”不等于“可以继续交易”。商品计价信息等关键依赖失败时应禁止提交并提供重试；可选信息可以降级。不能只因为用了 allSettled 就声称容错完全可靠。

### Q13：Pinia 和本地缓存分别负责什么？

Pinia 为页面提供响应式用户状态，本地缓存支持重启后恢复登录信息。当前用户 store 同步 token、用户 ID 等字段，部分临时 UI 状态不持久化。

难点是两者保持一致：登录、退出、失效都应经过统一入口。缓存里的身份字段只能用于界面和请求上下文，服务端不能信任客户端传入的 account_id 来授权。

### Q14：小程序为什么不能直接像网页一样跳外部 App？

受到微信平台和操作系统能力约束。项目对 iOS 使用 web-view 桥接及微信开放标签，对 Android 提供外部浏览器引导，再通过 Intent 和下载地址兜底，并不是任意链接都能直接唤起。

JSSDK 签名 URL 要与实际页面一致且去除 fragment，还依赖业务域名、开放平台绑定和开放标签配置。需要覆盖安装 / 未安装 App、不同系统和浏览器，不能只通过桌面浏览器测试就承诺兼容。

## 5. 可以展开的三个技术案例

以下是基于代码的技术讲解模板，不代表已经核实的个人线上事故。若确实亲历，再补充真实背景和处理过程。

### 案例一：会话切换造成失效响应竞态

- 场景：请求返回顺序与用户登录操作顺序不一致。
- 原因：将所有 401 都解释为“当前登录失效”。
- 实现：请求携带会话快照，响应处理时比较当前会话，再决定是否清理；跳转单独防重。
- 验证方式：延迟 A 的接口响应，登录 B 后再返回 A 的 401，检查 B 的 token 和页面是否保留。
- 延伸：可以用统一 sessionVersion 覆盖旧请求成功结果、失效响应和页面状态写入。

### 案例二：大整数订单 ID 被悄悄改写

- 场景：接口原始 ID 正确，页面使用或再次提交时 ID 改变。
- 原因：JSON 解析阶段已经越过安全整数范围，字符串转换太晚。
- 实现：保留原始文本，按需使用 json-bigint 精确回读，统一 ID 类型。
- 验证方式：覆盖安全整数边界、超大 ID、嵌套对象、数组和非 ID 大数字；验证请求提交不丢位。
- 延伸：最优接口契约仍是后端把标识符明确返回为字符串，客户端防御只是兼容措施。

### 案例三：支付链路不应只有成功 / 失败两种状态

- 场景：订单已创建，但用户取消支付或网络在支付后中断。
- 原因：把下单、支付调用和到账确认揉成一个布尔值。
- 现有实现：统一支付入口，区分取消与失败，对已有订单提供再次支付。
- 后续完善：服务端查单、确认中状态、幂等键、超时恢复；这些属于建议，不要讲成已实现。
- 验证方式：模拟取消、参数缺失、支付超时以及支付成功后回调延迟，检查是否错误创建新订单。

## 7. 建议准备的验证用例

以下是面试前建议补做的验证，不是本次已执行测试结果。本次只进行了源码阅读和资料整理，没有执行真实支付、提现或外部 App 唤起。

| 场景 | 关键观察点 |
| --- | --- |
| 多请求同时返回登录失效 | 不重复弹窗、不循环跳转，状态能恢复 |
| A 请求延迟，B 已登录后 A 返回 401 | 不清空 B 会话 |
| 公开页 token 过期 / 受保护页未登录 | 浏览边界与登录回跳正确 |
| 超大整数 ID 与嵌套 ID | 精确保持原始数字串，不静默舍入 |
| 非白名单不安全数字、非法 ID | 明确报错，不把错误数据传到下游 |
| 个人价与批量价混合、渠道优惠与券 | 折扣范围与互斥规则正确 |
| 商品信息失败但地址成功 | 不以不完整计价数据继续下单 |
| 连续点击提交、提交异常后重试 | 当前页面不重复发起，异常后按钮恢复 |
| 支付取消后再次支付 | 使用原订单，不把取消支付当作取消订单 |
| 下单成功后地址保存失败 | 保留订单信息，可继续支付，避免重复下单 |
| 提货无运费 / 需付运费 / 运费券 | 分支和订单跳转一致 |
| iOS / Android，App 安装 / 未安装 | 唤起条件、外部浏览器引导和下载兜底正常 |

项目提供 type-check 和各平台构建脚本，但编译通过不能代替上述业务验证；不能仅因存在测试相关依赖就宣称已有完整测试体系。

## 8. 与 Agent 岗位如何衔接

这个项目本身不是 Agent 项目，不包含已核实的 RAG、工具调用或智能体编排能力。它的作用是证明商业前端交付与复杂交互处理能力，与 ReproLens、TraceBase、Sift 等项目形成互补。

可以这样回答：“这个项目体现的是交易流程、异步状态、接口契约和平台集成能力；Agent 项目体现模型与工具编排。两者都需要明确的状态边界、异常恢复和可验证结果，但我不会把普通业务接口包装成 Agent。”

如果被问未来能否接入 AI，可以提议商品问答、订单查询助手，但应强调最小权限、基于真实订单数据回答，以及支付、提现等高风险操作必须由用户明确确认。这属于未来构想，不是当前成果。

## 9. 面试前速查清单

- 准备真实的参与时间、团队分工和个人负责范围，不照抄整个项目为个人贡献。
- 能独立讲清“购买”和“库存提货”的区别。
- 能画出旧会话请求晚于新登录返回的时序。
- 能解释为什么大整数解析后再转字符串已经太晚。
- 能说明优惠作用于哪些商品、为什么支付金额必须由后端核定。
- 能区分订单创建、支付调用、取消支付、最终到账与再次支付。
- 准备一段可脱敏展示的操作录屏，不在现场暴露凭据或执行真实支付。
- 若没有可靠统计，不写用户量、转化率、性能提升比例和零故障承诺。
- 先处理 OSS 凭据风险，再考虑公开源码或现场展示该文件。

### 重点源码阅读顺序

1. src/pages.json：业务模块地图。
2. src/pages/cart/submit.vue：商品元数据、优惠计算、提交锁及下单流程。
3. src/utils/index.ts：支付参数适配、再次支付与平台跳转。
4. src/api/request.ts：原始文本解析、数字规范化、会话快照与失效处理。
5. src/utils/auth-route.ts、src/store/user.ts：页面访问控制和用户状态同步。
6. src/pages/basket/confirm.vue：提货申请及运费支付分支。

最值得记住的四句话：登录失效要对准产生请求的会话；大整数要在解析丢精度之前处理；前端防重不等于服务端幂等；支付回调不等于最终到账。
