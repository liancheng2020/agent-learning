# Frontend Review Agent：10 个面试题答案

## 1. Agent 和普通 Chatbot 的区别是什么？

Chatbot 的核心是根据上下文生成回复；Agent 还要围绕目标做决策、调用工具、读取外部状态、处理失败并产出可验证结果。本项目不是只让模型“点评代码”，而是让审查流程调用知识检索、返回规范引用、记录 Trace，并在 Patch/部署前进入人工审批。

## 2. 为什么选择 FastAPI 和 Pydantic？

FastAPI 适合把 Agent 能力暴露为清晰 API，自动生成 OpenAPI，测试也方便。Pydantic 在输入和输出边界做 Schema 校验，能拒绝缺字段、类型错误和超长输入。稳定 JSON 不能只靠 Prompt，必须让 Provider 的结构化输出和服务端 Schema 校验共同兜底。

## 3. RAG 为什么会答错，怎么评估？

常见原因包括文档质量差、Chunk 边界错误、Embedding 不匹配、过滤条件过严、召回不足、重排错误和模型忽略引用。本项目用固定数据集评估问题命中率、引用正确率和 Case 通过率，而不是凭感觉看答案；失败样本要区分“规则没发现”“检索没召回”“引用不正确”再分别调整。

## 4. Tool Calling 失败时如何处理？

先区分参数错误、超时、依赖错误和业务无结果。参数错误直接拒绝；瞬时错误可有限重试；非关键工具允许降级；影响依据正确性的工具失败时要停止无依据推断。每次失败都返回稳定错误码、用户建议和 `traceId`，并在 Trace 记录参数摘要、耗时和错误栈。

## 5. 如何保证 Agent 输出稳定 JSON？

第一层使用结构化输出或 JSON Schema 约束模型；第二层用 Pydantic 校验类型、枚举、长度和必填字段；第三层只允许有限重试，仍失败则返回 `MODEL_JSON_INVALID`，绝不把半截 JSON 当成功结果。Schema 还应版本化，避免前后端发布节奏不同造成兼容问题。

## 6. 怎么知道一次 Agent 运行为什么失败？

每次运行生成唯一 `traceId`，按阶段记录 `run.started`、缓存、工具调用、审批和 `run.completed/failed`。Trace 包含模型、Prompt 版本、工具入参/结果摘要、耗时、token/cost 和错误栈。排查时先定位失败阶段，再对比同输入在不同 Prompt/知识库版本下的行为。

## 7. 为什么高风险操作需要人工审批？如何避免重复执行？

模型输出存在不确定性，生成 Patch、应用修改和生产部署都有真实副作用，因此推理与执行必须分离。审批只能从 `pending` 原子转换到 `approved` 或 `rejected`；执行时同时检查动作、审批状态和结果是否为空。拒绝后不能覆盖决定，执行过的审批不能再次执行。

## 8. Redis 在项目里解决什么问题？为什么需要降级？

Redis 只缓存“完整 Diff + Prompt 版本”相同的审查结果，避免重复检索和计算，没有为了技术栈再塞会话或限流。缓存不是正确性依赖，所以 Redis 断连时回退进程内 TTL 缓存，核心审查继续可用。知识库或模型版本变化时，也应加入缓存 key 或主动失效。

## 9. Docker Compose 中四个服务如何分工？

Nginx 提供前端静态资源并代理 `/api`；FastAPI 运行 Agent 和业务 API；PostgreSQL 保存审批数据，pgvector 保存知识向量；Redis 负责 TTL 缓存。健康检查和 `depends_on` 控制启动顺序，持久卷保存数据库、缓存和 Trace，`.env.example` 记录所有外部配置。

## 10. 这个项目距离生产环境还差什么？

主要缺口是真实 LLM/Embedding 的容量与成本验证、身份认证与 RBAC、审批审计导出、密钥托管、分布式 Trace/OpenTelemetry、任务队列、并发压测、数据迁移与备份、Prompt/知识库版本治理。回答时要明确当前项目验证的是工程骨架和故障边界，不把本地 12 条评测结果等同线上质量。

## 复习标准

每题先用一句话给结论，再结合本项目讲一个具体实现，最后补一个生产环境改进点。能在 60-90 秒内回答且不背代码，才算真正掌握。
