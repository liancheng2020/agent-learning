01 / CANDIDATE POSITIONING

从前端工程师，走向 AI 应用开发

这份指南对应桌面的 4.0 排版版简历，以及三个公开项目。重点不是背术语，而是能沿着一次真实请求解释输入、决策、工具、证据、失败和边界。

90 秒自我介绍，可按事实调整

我有 7 年以上前端开发经验，做过中后台、H5 和小程序，也有 Node.js API 实践。最近把重点放在 AI 应用工程：ReproLens 用模型辅助生成受限的浏览器复现计划，人工确认后由 Playwright 执行和采证；TraceBase 解决项目资料的检索、引用与更新一致性；Sift 处理 YouTube、文件和长文本，输出可回查的结构化摘要。这三个项目分别让我实践了 Agent 的受控执行、RAG 的证据约束，以及多源内容的解析和模型输出校验。我目前更适合 AI 应用开发或 AI 全栈岗位，不会把个人项目包装成生产级多租户平台。

面试官最可能先判断的三件事

你真正做了什么

说清模型、规则、工具、人工确认各自的职责；AI 辅助编码不是问题，无法解释实现才是问题。

问题怎么验证

拿出固定场景、自动测试、失败注入和可重复演示。不要把“页面能打开”说成“效果已验证”。

边界在哪里

明确本机运行、单用户、输入格式、权限和真实模型依赖；下一步改进要有原因和优先级。

简历事实基线：前端经验、Node.js 实践、三项目架构与技术栈来自桌面 4.0 排版版。页面不包含手机号、邮箱等个人联系方式。

02 / CONTROLLED BROWSER AGENT

ReproLens：如何让 Bug 复现有证据

核心不是“让模型看一眼网页猜 Bug”，而是把自然语言问题变成经人确认的有限步骤，再用真实浏览器检查预期和实际是否一致。

两分钟项目讲述

前端或测试收到“购物车点了加购没反应”时，单靠描述很难复现。我做了 ReproLens：输入目标 URL、问题、预期和设备；可选观察页面结构，DeepSeek 给出候选计划；服务端用 Zod 校验动作和定位参数，用户编辑确认后，Playwright 在桌面或手机视口顺序执行。每一步保存状态、期望、实际值和截图，并通过 SSE 展示执行进度。修复后复用相同计划、设备和预期重跑，只有基线确实复现且本次核心检查全部通过，才给出范围内的修复通过。遇到定位歧义、前置条件失败、浏览器缺失，返回证据不足或执行受阻，而不把它们说成产品 Bug。

一次请求的数据流
问题 + URL + 预期→模型候选计划→Zod + 人工确认→Playwright 执行→证据 + SSE→同标准复测
01规划

模型只提出计划，不执行任意 JavaScript。页面观察只提取受限元素信息，不直接把整页 DOM 喂给模型。模型失败回待编辑模板，不能算规划成功。

02确认

计划最多 15 步，动作限制为 click、input、assert、reload；目标可用 label、placeholder、text、role 或 CSS。用户检查定位、预期和风险后再执行。

03执行

每设备隔离浏览器上下文，逐步定位并断言。输入失焦丢值靠真实键盘输入与失焦后读取；遮挡靠视口边界和中心命中检查。

04判定

区分 reproduced、not_reproduced、inconclusive 与执行失败。修复验证核对完整计划、设备、问题和预期，再按步骤证据比较。

关键代码路径

repro-plan.ts / provider.ts
计划契约、模型输出校验与降级
scanner.ts / business.ts
浏览器动作、定位和业务断言
business-verification.ts / run-manager.ts
同标准复测、状态与事件

可以现场演示的最小闭环

  1. 打开内置“购物车数量不变”的缺陷版本。
  2. 确认固定计划并运行，指出失败的核心断言及实际值。
  3. 切到修复版本，沿用同计划复测，查看步骤比较与修复结论。
  4. 故意让目标歧义或卸载浏览器，说明为何不能误报为 Bug。

简历中“54 条单测、11 个本机浏览器任务”是当时的验证快照；面试前需重新运行并核对当前报告，不把数字当永久保证。

面试官会追问
这算 Agent 吗？模型是不是在自主调用工具？

属于受控的 Agent 应用工作流：模型参与计划生成，执行器按确认计划调用浏览器能力。但它不是多轮原生 Tool Calling 或自主探索 Agent；模型不直接控制 Playwright，也不在执行中自动重规划。这样设计是为了把风险和结果归因控制在可解释范围内。

为什么已经有 JSON Schema，还需要 Zod 和人工确认？

三层解决不同问题：模型 JSON 模式提高格式稳定性；Zod 检查步骤类型、字段、长度等程序契约；人工确认检查业务语义，例如按钮是否找对、期望是否真实、点击是否有副作用。合法 JSON 不等于正确复现计划。

如何避免“网页打不开/定位不到”被误判为 Bug？

先看浏览器是否可启动、页面和前置条件是否成立，再看核心断言。定位歧义、超时、页面不可访问归入执行受阻或证据不足；只有实际跑到目标断言且与预期不符，才判目标路径 reproduced。业务结论和执行状态分开存。

为什么修复验证要用同一计划？只看截图变化不行吗？

截图变化只说明像素不同，不能说明业务恢复。复测必须保留计划、设备、问题和预期，并要求基线有核心失败、本次相关步骤完整通过；缺步骤或标准变化都不能判通过。视觉 Diff 是辅助信号，不能覆盖业务断言。

遮挡检查与网络断言的可信度有多高？

中心命中和边界检查能发现有限的遮挡与出视口问题，不保证设计稿级像素一致。网络检查依赖操作后同源路径、方法及唯一匹配，时间关联不证明后端因果。对于复杂异步、跨域、动画和响应复用，需要更细的观察或人工核查。

为什么不直接部署成公开 SaaS？

浏览器执行任意 URL 有 SSRF、内网访问、资源耗尽和证据泄露风险。当前定位是本机或可信测试站点；公开部署需要认证、URL/DNS/IP 约束、隔离 Worker、配额和证据权限保护。计划确认并不等于完整的安全边界。

不要夸大：不自动改源代码、不通用探索网站、不支持任意拖拽或验证码；手机测试是 Chromium 视口模拟，不是真机 Safari。生成 Playwright 测试文件也不等于它已被自动重跑。
03 / EVIDENCE-BOUND RAG

TraceBase：知识库为什么要可追溯

项目文档会更新，答案却容易引用旧资料。TraceBase 的重点是从“检索得到片段”进一步做到“版本有效、原文可核查、证据不足时不编造”。

两分钟项目讲述

我做了一个本机运行的项目知识库，支持 Markdown、TXT、静态 HTML 和文字型 PDF。文档入库后按标题或页码切分，保存来源和版本；问题先做关键词检索，可选接入独立 Embedding 服务做向量检索，两个列表用 RRF 融合，最终取最多 6 段证据。DeepSeek 只基于候选证据生成回答，模型使用 S1–S6 这样的短编号选来源，服务端再映射到真实片段，并检查引用 ID 和逐字原文。没有候选就拒答；模型不可用或输出不合法时展示摘录并明确降级。资料更新时新片段准备好后事务切换 active_revision，失败保留旧版；回答保存前再次检查引用仍指向有效版本。这样用户可以定位原文，但我不把“引用字符串存在”说成“推理一定正确”。

一次问答的数据流
上传文档→提取 / 分块 / 版本→关键词 + 可选向量→RRF Top 6→模型回答→引用核验 / 保存
01入库

原文件和 revision 入库；索引任务提取正文并分块，保留标题、页码及抽取警告。向量模型有独立配置，DeepSeek 聊天接口不自动提供 Embedding。

02检索

关键词和向量各取最多 18 条候选，用 1/(60+rank) 做 RRF 累加，取 Top 6。向量服务不可用时回到关键词；RRF 分数是排序用，不是正确率或置信度。

03生成与校验

模型基于有限证据输出结构化段落；程序核对来源 ID、引用逐字包含于原片段。无证据时拒答；无 Key、超时或引用错误时回退为原文摘录并说明原因。

04版本一致性

新版索引事务切换后才对外生效；失败保留旧版。回答入库前再验证证据属于当前 active_revision，防止生成期间资料更新造成悬空引用。

关键代码路径

documents.ts / library.ts
提取、分块、索引、版本切换
search.ts
关键词 / 向量检索、RRF 和回答保存
models.ts / answer-evidence.ts
模型调用、结构校验、引用核验

可以现场演示的最小闭环

  1. 创建知识库并导入一份有章节的示例文档。
  2. 问一个文档里有答案的问题，打开引用定位原文。
  3. 问一个文档没有回答的问题，展示拒答或资料不足。
  4. 更新同名资料，观察有效版本和历史回答的提示。

仓库演示视频使用无 Key 的关键词检索与摘录，不代表真实模型生成效果；面试时需要分开说明。

面试官会追问
为什么同时做关键词和向量？RRF 为什么合适？

关键词对专有名词、错误码和精确字段更稳定；向量对同义表达更有帮助。两路分数尺度不同，直接加权容易失真。RRF 只看各自名次，降低分数标定要求。但它不保证召回充分，也不能把排序分当答案置信度；效果需要固定数据集验证 Recall@k 和引用支持率。

为什么版本切换要用事务？Embedding 调用为什么放事务外？

事务让“新片段写入 + active_revision 切换”要么一起完成，要么一起失败，避免用户检索到半成品。外部 Embedding 调用慢且可能失败，放进事务会长时间持锁；先准备新索引，再短事务提交，并在提交前确认 revision 未被后续上传覆盖。

引用校验能解决幻觉吗？

只能保证引用 ID 存在、引文是该片段的连续原文，不能证明这句话支持了生成的结论，更不能保证资料本身真实。下一步应做独立的支持性标注集，统计引用支持率、无答案识别和人工纠错案例。

索引时向量服务挂了会怎样？

词项索引仍可提交，用户看到警告，问答走关键词检索；已有向量的模型标识和维度必须与查询端匹配。更换 Embedding 模型后需要重建索引，不能直接混用不同向量空间。

用户提问过程中，文档被更新或删除了怎么办？

检索时只查 active_revision；生成后保存回答前，在事务里再查一次证据仍属于有效版本。若失效，清除本次回答的证据与结论并提示重问。历史回答保留当时快照，打开旧引用时标明历史版本。

PGlite + pgvector 与线上 PostgreSQL 有什么差别？

PGlite 在本机进程内提供真实 SQL、事务和向量距离能力，适合单机作品；不等于远程 PostgreSQL 服务，也没有多进程共享、HA 或大库 ANN 性能保证。当前检索是小规模精确扫描，团队版才需要权限、远程数据库、队列和独立解析沙箱。

不要夸大：知识库分组不是权限隔离；默认全局问答会检索全部库。没有 OCR、GitHub 增量同步或生产级多租户。上传文档可能外发给模型或 Embedding 服务，敏感资料必须先评估。
04 / MULTI-SOURCE DIGEST

Sift：从多源内容到可核查摘要

真正难点不只是“调用模型总结”，而是每个来源怎样提取正文、长内容怎样控上下文、输出怎样结构化，以及线上环境失败时怎样让用户知道原因。

两分钟项目讲述

Sift 接收 YouTube 视频链接、PDF/Word 等文件或粘贴文本，把它们转为有段落或时间标记的正文，再用 DeepSeek 或可选 OpenAI 生成统一结构：结论、重点、数据、行动、风险与来源定位。长内容先按段落或时间标记切分，分段提炼，再合并去重；输出通过 JSON Schema 和运行时校验，DeepSeek 返回非法 JSON 时只定向修复一次，仍失败就明确报错。线上 YouTube 解析优先由 Supadata 获取公开字幕，无字幕时尝试转写；PDF 放在浏览器解析以适配 Serverless。服务端以 NDJSON 返回进度，同时对输入长度、文件大小、超时做约束。项目保留原文定位，提醒用户核查重要结论。

一次摘要的数据流
视频 / 文件 / 文本→解析 + 定位标记→分段摘要→合并去重→Schema 校验→结果 + 溯源
01源解析

文本直接进入流水线；PDF 浏览器侧解析；视频先取字幕或转写。浏览器安装的代理不会自动作用于服务端，Vercel 的 127.0.0.1 更不是用户本机代理。

02长内容

保留段落编号或时间戳再切块，逐段提炼可举证信息，最后合并去重。分段能够控制上下文，但跨段关系可能损失，最终结论需要回查来源。

03结构输出

模型提示约束 JSON Schema，程序仍需解析和字段校验。DeepSeek 非法输出只做一次有针对性的修复；失败不硬凑一个“看起来正常”的摘要。

04部署反馈

NDJSON 展示解析、转写与摘要进度；区分超时、额度不足和内容缺失。实例内缓存、IP 限流不是分布式保护，多实例下不能宣称全局一致。

关键代码路径

youtube.js / content.js
视频来源与内容切分
summarize.js
模型调用、Schema、分段合并与错误
server.js / public/app.js
API、NDJSON 流与前端反馈

可以现场演示的最小闭环

  1. 粘贴一段可控文本，切换摘要深度并核对关键数据。
  2. 上传文字型 PDF，查看段落定位与导出 Markdown。
  3. 用可访问视频展示时间轴；准备失败样本解释字幕/转写边界。
  4. 断开模型 Key 或模拟异常，展示明确错误而非空白页面。

线上视频依赖第三方可访问性和额度；演示前准备已验证的公开视频，文本链路作稳定兜底。

面试官会追问
为什么不能把整个长文一次丢给模型？

上下文窗口、费用、延迟和截断风险都会增加。按段落或时间切分后分段提炼，再合并去重能把成本控制在可预测范围；代价是跨段推理容易遗漏，因此保留来源标记、限制单段结论并允许用户回查。

模型已经开启 JSON Schema，为什么还要本地校验？

模型或兼容 API 仍可能返回截断、非 JSON、缺字段、类型错或语义不合格内容。服务端才是契约最终守门人：解析、限制列表数量与字段长度、验证结构；修复一次是受控补救，不是无限重试。

为什么本机能解析 YouTube，Vercel 却不行？

浏览器、Node 服务端、云函数的网络路径不同。本机浏览器可访问不代表 Vercel 出站也可访问；把本机代理 URL 写到云环境会指向云函数自身。Sift 线上用字幕/转写服务，但仍受视频限制、第三方额度和响应超时影响。

为何把 PDF 解析移到浏览器？有什么代价？

这是适配 Serverless 部署的工程权衡：减少函数端 PDF 依赖和环境兼容问题，上传前即可提取文字。代价是客户端资源消耗、复杂排版与扫描件识别不可靠；OCR 当前不支持，不能声称所有 PDF 都能解析。

NDJSON 和 SSE 有何不同，为什么项目用 NDJSON？

两者都能增量传输；NDJSON 是每行一个 JSON 对象，适合 POST 摘要请求中顺序返回阶段和最终结果；SSE 使用 text/event-stream，有 event/id 等语义，适合单向事件订阅。关键在于前端增量解码、断线/异常处理和服务端及时 flush，而不是名称本身。

能保证摘要“深入、准确”吗？

不能保证。Schema 保证形状，不保证观点正确；来源片段和时间戳方便核查，不证明推理充分。应建立多源评测集，分别看事实保真、关键点覆盖、引用正确、冗余和延迟，对高风险内容要求原文复核。

不要夸大：当前每次只处理一个来源、不保存历史；YouTube 频道订阅和邮箱自动抓取尚未实现。实例内缓存和限流不适合声称分布式生产可用。
05 / ENGINEERING CROSS-EXAMINATION

把三个项目串成技术判断

这部分适合二面或架构追问。回答时先给结论，再说实现细节、失败路径与适用边界。

三个项目中，哪里真正有 Agent，哪里只是 LLM 工作流？

ReproLens 有模型规划、人工确认、受限浏览器执行与反馈，接近受控 Agent；但没有模型多轮 Tool Call 自主重规划。TraceBase 是证据约束的 RAG 问答，Sift 是多源解析和摘要流水线。不能因为接了 LLM 就都叫自主 Agent。

如果模型回答错，先查哪里？

按链路拆：输入是否解析正确；检索/页面观察是否漏掉关键上下文；Prompt 与模型返回什么；Schema 是否通过；引用和业务断言是否匹配；前端是否显示了正确状态。TraceBase 先看候选证据，Sift 先看原文与分段，ReproLens 先看确认计划及步骤证据。

为什么三项目都要“证据”和“拒绝冒进”？

模型可以流畅地输出错误结论。ReproLens 没有完整核心检查就不判修复；TraceBase 没有资料就拒答、引用异常就降级；Sift 解析或 Schema 失败就报错。边界约束使系统的失败可解释、可追溯，而不是静默地生成好看的结果。

如果要做成团队可用产品，下一步优先补什么？

先按风险补基础设施：ReproLens 是浏览器沙箱、认证、配额和证据权限；TraceBase 是文档访问权限必须在检索前过滤、持久任务队列与真实语料评测；Sift 是分布式限流/缓存、第三方服务配额与上传安全。不是先堆更多框架。

如何设计一套小而可信的评测？

每项目固定输入、期望与失败分类，保留未见样本：ReproLens 看计划可执行率、核心断言覆盖、误报/漏报；TraceBase 看 Recall@k、引用支持率、无答案识别；Sift 看事实保真、关键点覆盖、JSON 合法率与延迟。规则/Mock 测试和真实模型对照要分开报告，并标注样本规模。

使用 Codex/Kimi 辅助开发，怎么证明你不是只会“vibe coding”？

现场解释一个模块的输入输出和不变量，展示失败用例与测试，说明某个具体设计取舍及其代价；面对未知追问能定位源码和证据。可以诚实承认 AI 辅助编码，但核心架构、边界、验收由自己负责。面试前至少能脱离 AI 写出一条小型工具调用、校验或检索闭环。

一句话区分：ReproLens 的关键正确性是“执行是否真的覆盖了目标 Bug”；TraceBase 是“回答是否可由有效版本的原文支持”；Sift 是“多源内容是否正确解析并被忠实压缩”。
常见失误：把结构校验当事实校验、把检索命中当答案正确、把模型给出的计划当已经执行、把视觉变化当修复成功。
